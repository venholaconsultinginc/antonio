## What this repo is

`antonio` is a small, public set of Python example scripts ("seed" examples) showing how to query
a **Cordelia** SQLite database and produce basic report plots. It is not a maintained analytics
tool. Read `docs/objectives-and-requirements.md` for the objectives and explicit non-goals, and
`docs/plan.md` for the phased scope of work, the exact schema detail, and the encoding gotchas
below — both docs are the source of truth for scope decisions, not this file.

**Namesake:** Antonio, the sea captain in *Twelfth Night* who stakes Sebastian with support to get
going, then lets him make his own way — the intended relationship between this repo and its users.
It's one repo in a larger Shakespeare-named family (see the sibling `cordelia`, `goneril`, etc.
repos), but unlike the rest of that family this one is genuinely public on GitHub, not a private
Fossil repo with just a public overview page.

## Data source: Cordelia's SQLite schema

Cordelia (the sibling `../cordelia` C++ project) parses Garmin `.FIT` files into ~120 SQLite
tables, one per FIT message type. This repo only ever touches seven of them — `FileID`,
`Activity`, `Event`, `DeviceInfo`, `Session`, `Lap`, `Record` — the set one running activity
populates. Full column-level detail is in `docs/plan.md`; if you're touching `cordelia_db.py` or
the generator, read that first.

**Before trusting any schema detail here or in `docs/plan.md`: it was captured from `cordelia` on
2026-08-05 and is not guaranteed current.** If you're changing the generator or helper module,
diff the relevant `CREATE TABLE` statements in `../cordelia/src/records/*.cpp` against what's
copied here first — `cordelia` is under active development and this repo does not track it
automatically.

Three encoding rules matter more than anything else in this codebase, because getting them wrong
produces a database that opens fine but is silently corrupt:

1. **GPS is semicircle-encoded**, not plain degrees: `position_lat`/`position_long` are `INTEGER`
   int32, `semicircles = round(degrees * 2^31 / 180)`.
2. **Two time encodings coexist and must stay consistent with each other**: `Timestamp`-style
   columns are fixed 19-char TEXT `YYYY-MM-DDTHH:MM:SS` (UTC, no offset); `Session.start_time` and
   similar `INTEGER` fields use the **Garmin epoch** (seconds since 1989-12-31 UTC, i.e. Unix time
   minus `631065600`). Nothing in the schema enforces agreement between the two — that's on the
   code that writes them.
3. `FileID` requires a distinct `(serial_number, time_created)` pair per activity.
4. **`Lap.start_time` is declared `TEXT` but isn't an ISO 8601 string** — `cordelia` itself binds
   it as a plain Garmin-epoch `int32` (`cordelia/src/records/lap.cpp:903,1426`), same as
   `Session.start_time`. SQLite's `TEXT` affinity then stores it as text digits of that integer.
   Write it as an unquoted Garmin-epoch integer literal, not a formatted date string.

All conversions belong in `cordelia_db.py`, not reimplemented per script. When deriving a
Garmin-epoch integer from the same instant as an ISO 8601 TEXT column, use
`cordelia_db.naive_utc_to_unix()`, not `datetime.timestamp()` — the latter interprets a naive
datetime in the host machine's local timezone and will silently make the two encodings disagree
depending on where the script runs (caught during this repo's own Phase 5 validation).

## Style

This is example/seed code meant to be read and copied by someone learning the schema, not a
library. Favor clarity over abstraction: prefer three similar, obvious scripts over one clever
parameterized one. Every report script should be readable top-to-bottom on its own.

## Data hygiene

Never commit a real Cordelia export or any file containing real personal fitness data — synthetic
data generated by `generate_sample_data.py` only. The generated `.db` output is not committed;
regenerate it locally instead.

## Running

```bash
python3 generate_sample_data.py                 # writes output/sample_data.sql, stdlib only
sqlite3 mydb.sqlite < sql/create_tables.sql
sqlite3 mydb.sqlite < output/sample_data.sql
```

Report/plotting scripts (Phase 3 in `docs/plan.md`) don't exist yet — `requirements.txt`
(pandas, matplotlib) is a forward declaration for them, not needed by the generator itself.

No test suite — validation is running the pipeline end to end and checking the output looks sane
(closed-loop route, pace/HR/cadence/temperature within their +/-10% bands, ~5 km/day, the
Garmin-epoch and ISO 8601 time columns agreeing with each other), per `docs/plan.md`'s Phase 5.
